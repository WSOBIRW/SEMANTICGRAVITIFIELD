# Формат журнала событий SGF

## 1. Назначение

Журнал SGFJ фиксирует последовательность входных рыночных событий и управляющих операций, изменяющих состояние валидатора. Он используется для детерминированного воспроизведения состояния после snapshot.

Журнал не выбирает торговые действия, не выполняет сетевой ввод-вывод и не владеет файловым backend. Он не гарантирует долговечность записи без внешнего storage-протокола.

## 2. Формат SGFJ v1

Каждая запись имеет framing:
- длина тела: unsigned 32-bit little-endian;
- тело записи;
- SHA-256 digest тела: 32 байта в конце тела.

Тело начинается с magic ASCII SGFJ, версии unsigned 16-bit little-endian (1), offset unsigned 64-bit little-endian, SHA-256 предыдущей записи (32 байта) и типа операции (1 байт).

Первая запись пустого журнала имеет offset 0 и предыдущий hash из 32 нулевых байтов. Следующая запись увеличивает offset на единицу. Offset относится к записи, а не к размеру файла.

## 3. Типы операций

### 0 — MarketEvent

После типа операции кодируется schema_version (u16), event_id/source_id/instrument_id (длина u32 + UTF-8), event_time_ms/received_time_ms (i64), sequence (tag 0 = отсутствует, tag 1 + u64 = присутствует), payload:
- tag 0: Quote, bid_ticks i64, ask_ticks i64, price_scale u32;
- tag 1: Trade, price_ticks i64, quantity_lots u64, price_scale u32.

Семантическая проверка события выполняется тем же EventValidator, что используется при обычном приёме.

### 1 — ResetStream

После типа операции кодируются source_id и instrument_id как строки длина u32 + UTF-8. Replay применяет reset_stream к указанной паре. Операция обязательна в журнале, если live-процесс вызвал сброс watermark после точки snapshot. Иначе последующие события с новой sequence могут быть ошибочно отвергнуты при replay.

Неизвестный тип операции отклоняется.

## 4. Цепочка целостности и checkpoint

Каждая запись содержит hash предыдущей записи и собственный SHA-256. Это выявляет повреждение, перестановку и вставку записей без пересчёта всей цепочки.

JournalCheckpoint содержит:
- next_offset: offset следующей ожидаемой записи;
- last_hash: digest последней подтверждённой записи; нулевой digest для пустого журнала.

replay_journal требует два checkpoint:
1. anchor — checkpoint, непосредственно связанный с восстановленным snapshot;
2. expected_end — checkpoint конца сегмента из durable manifest.

Сегмент принимается только если его итоговый checkpoint точно совпадает с expected_end. Это позволяет обнаружить потерю целых последних записей, которую одна проверка framing/hash обнаружить не может.

Checkpoint нельзя выводить из самого переданного журнала при восстановлении: ожидаемое конечное значение должно поступать из независимо зафиксированного durable manifest.

## 5. Детерминированное восстановление

EventValidator::restore_and_replay(snapshot, journal, anchor, expected_end):
1. полностью проверяет и восстанавливает snapshot;
2. проверяет framing, версию, digest и hash-chain каждой записи;
3. требует непрерывные offsets;
4. воспроизводит MarketEvent через обычную валидацию;
5. воспроизводит ResetStream через reset_stream;
6. сверяет конечный checkpoint;
7. возвращает новый валидатор только при полном успехе.

При ошибке частично восстановленный валидатор наружу не возвращается. Низкоуровневый replay_journal изменяет полученный &mut self по мере обработки; если он возвращает ошибку, этот экземпляр необходимо отбросить. Для восстановления после сбоя следует использовать restore_and_replay.

## 6. Требования к storage adapter

Storage adapter должен обеспечивать согласованную фиксацию:
- snapshot bytes;
- anchor checkpoint, связанного с этим snapshot;
- текущего журнала после anchor;
- expected-end checkpoint.

Эти метаданные должны публиковаться как одна атомарная версия manifest. Нельзя сначала опубликовать новый checkpoint, а затем рассчитывать на запись журнала: авария между операциями создаст ложное подтверждение долговечности.

Безопасный протокол требует append/flush журнала до публикации manifest, подтверждающего запись. Для snapshot требуется временный файл/объект, проверка содержимого, затем атомарная публикация snapshot и соответствующего manifest. Конкретные гарантии fsync/rename/transaction зависят от backend и должны быть отдельно проверены.

SHA-256 не является MAC или цифровой подписью. Он не защищает от злонамеренной подмены с пересчётом цепочки, отката к старому manifest или удаления журнала. Эти угрозы требуют контроля доступа, аутентификации manifest и защиты от rollback на уровне storage.

## 7. Ошибки и запрет частичного восстановления

Журнал целиком отклоняется при усечённом framing или теле, неизвестной версии или типе операции, неверном magic, несовпадении digest, нарушении предыдущего hash, пропуске или повторе offset, несовпадении конечного checkpoint, некорректном UTF-8 или структуре события, семантической ошибке валидации события.

Автоматическое пропускание повреждённых записей и продолжение replay запрещено: это изменило бы смысл последовательности и могло бы скрыть потерю доказательств.
