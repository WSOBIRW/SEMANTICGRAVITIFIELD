# Файловый backend поколений восстановления SGF

## 1. Назначение

Документ задаёт проект первого конкретного RecoveryStorage backend. Backend использует файловые поколения и стандартный ввод-вывод Rust. Доменное ядро остаётся независимым от файловой системы.

## 2. Область ответственности

Backend отвечает за:
- долговечную запись snapshot, journal и manifest;
- атомарную публикацию текущего поколения;
- сериализацию конкурирующих writers;
- проверку поколения через compare-and-swap;
- восстановление после незавершённого commit;
- проверку пакета перед публикацией и после чтения.

Backend не отвечает за семантическую реконструкцию рынка, качество источников или торговые решения.

## 3. Чем не является

- SHA-256 не является аутентификацией и не предотвращает rollback.
- Атомарное переименование не гарантирует долговечность без sync данных и каталогов.
- Advisory lock не защищает от процесса, который намеренно игнорирует протокол блокировки.
- Текущая реализация на path-based std::fs не является песочницей от злонамеренного локального пользователя. Корневой каталог и его родительские компоненты должны находиться под контролем выделенной учётной записи и не быть доступны на запись недоверенным процессам. Для более сильной модели локального противника потребуются descriptor-relative операции, no-follow открытия и проверка владения/прав.
- Локальный файловый backend не обещает корректную работу на NFS/SMB и иных сетевых ФС без отдельной проверки их семантики.
- Отсутствие автоматической очистки старых поколений не является утечкой временных файлов: неизменяемая история сохраняется намеренно.

## 4. Структура каталога

Корневой каталог backend:
- `CURRENT` — атомарно заменяемый указатель на активное поколение;
- `.writer.lock` — постоянный файл межпроцессной advisory-блокировки;
- `generations/` — неизменяемые опубликованные поколения;
- `.staging-*` — уникальные временные каталоги поколений как непосредственные элементы корня; автоматическая очистка отключена;
- `.CURRENT-*` — временные указатели, зарезервированные через create_new до публикации поколения и заполненные/синхронизированные после его долговечной публикации; незавершённые файлы не считаются активным CURRENT и автоматически не удаляются.

Поколение имеет детерминированное имя из номера, например `g-00000000000000000042`, и содержит:
- `snapshot.bin`;
- `journal.bin`;
- `manifest.bin`.

CURRENT содержит версию указателя, generation и digest manifest. Формат CURRENT отдельный от SGFM и имеет собственную версию.

## 5. Протокол commit

1. Проверить входной RecoveryPackage через `validate()`. Валидация не изменяет пакет.
2. Открыть постоянный `.writer.lock` и получить эксклюзивную блокировку. Блокировка должна освобождаться ОС при закрытии дескриптора, в том числе при аварийном завершении процесса.
3. Прочитать CURRENT и фактическое активное поколение под блокировкой.
4. Выполнить `validate_generation_transition(expected, actual, candidate)`. При несовпадении вернуть GenerationConflict. Только непосредственный successor допустим.
5. Проверить, что целевой generation directory отсутствует. Любое существующее поколение сохраняется и приводит к отказу, пока не доказано, что оно безопасно для удаления или повторного использования. Незавершённые staging-каталоги в текущей реализации автоматически не удаляются.
6. Создать уникальный staging-каталог как непосредственный элемент корня хранилища, без промежуточного изменяемого каталога `.staging/`. Создание должно завершаться ошибкой при совпадении имени, без перезаписи чужих данных.
7. Записать snapshot, journal и manifest. Для каждого файла выполнить write_all и sync_all. После этого синхронизировать staging-каталог.
8. Проверить отсутствие целевого generation directory. Зарезервировать уникальное имя временного `.CURRENT-*` через `create_new` до публикации поколения. Это исключает коллизию старого временного имени после перезапуска процесса уже после создания orphan generation.
9. Переименовать staging directory в неизменяемый каталог поколения. Источник и назначение должны находиться на одной файловой системе. Синхронизировать generations directory.
10. Записать в ранее зарезервированный временный CURRENT номер поколения и digest manifest; выполнить sync_all.
11. Атомарно заменить CURRENT временным файлом. Синхронизировать корневой каталог.
12. Только после успешной публикации вернуть Ok и освободить блокировку.

Порядок важен: сначала долговечное поколение, затем указатель. Сбой до шага 10 оставляет прежний CURRENT активным. Сбой после атомарной замены CURRENT должен приводить к выбору нового полного поколения после проверки. Backend никогда не должен собирать пакет из файлов разных поколений.

## 6. Восстановление и очистка

При открытии:
1. проверить CURRENT и его версию;
2. прочитать указанное поколение;
3. проверить соответствие generation и manifest digest;
4. выполнить `RecoveryPackage::validate()`;
5. только после успешной проверки вернуть пакет потребителю.

Незавершённые каталоги `.staging-*` не считаются поколениями. Текущая реализация оставляет их нетронутыми. Они являются непосредственными элементами корня, поэтому отдельный изменяемый каталог staging не участвует в публикации. Безопасная очистка всё равно потребует закреплённого no-follow дескриптора и операций относительно него. Каталог поколения, не указанный CURRENT, может быть orphan после сбоя между публикацией поколения и CURRENT; он не активен, не должен автоматически выдаваться как current и не должен перезаписываться.

В первой версии автоматическое удаление старых опубликованных поколений не реализуется. Это исключает гонки с читателями и сохраняет историю. Политика retention вводится отдельным этапом с явными гарантиями для активных readers и recovery points.

## 7. Конкурентность

Используется OS advisory file lock на постоянном lock-файле. Файл блокировки нельзя удалять и создавать заново во время работы: разные процессы могли бы заблокировать разные inode одного и того же пути.

Lock удерживается от чтения actual generation до публикации CURRENT и sync корневого каталога. CAS, проверенный до получения lock, не является достаточной защитой.

Читатели используют CURRENT и неизменяемые generation directories. Читатель проверяет manifest и package после открытия. Удаление поколений в первой версии отсутствует.

## 8. Сбой и долговечность

Тесты должны внедрять отказ после каждого шага commit:
- после создания staging;
- после каждого файла;
- после sync файлов;
- после sync staging directory;
- после публикации generation directory;
- после sync generations directory;
- после записи и sync временного CURRENT;
- после замены CURRENT;
- после sync корневого каталога.

После каждого сбоя load_current возвращает только предыдущее полное поколение или новое полное поколение. Повреждённое или смешанное поколение отклоняется.

Тесты процесса не доказывают поведение при потере питания и аппаратной неисправности. Гарантии зависят от ОС, файловой системы, mount options, накопителя и модели локального доступа. Текущий backend предполагает доверенный root path, недоступный на запись недоверенным локальным процессам. Production-документация должна явно указывать проверенную платформу и модель доступа.

## 9. Защита от rollback

Файловый CAS предотвращает потерю обновлений между сотрудничающими writers, но не защищает от восстановления старой копии всего каталога. Для защиты от злонамеренного rollback необходим независимый доверенный high-water mark вне того же failure domain. До реализации такого механизма backend честно заявляет только целостность и конкурентную согласованность в пределах локального хранилища.

## 10. Зависимость для блокировки

Для межпроцессной advisory-блокировки используется узкая библиотека `filelock`. Её синхронный режим поддерживает Rust 1.71; поэтому MSRV проекта повышается минимально с 1.70 до 1.71, а не до 1.89, где File::lock доступен непосредственно в std. Конкретная версия и лицензия фиксируются в Cargo.lock; дополнительные async/runtime функции не включаются.

## 11. Критерии соответствия

- CAS проверяется под той же блокировкой, которая удерживается до публикации.
- Два writer с одинаковым expected generation не могут оба успешно опубликовать successor.
- Успешный commit делает долговечными файлы и указатель в определённом порядке.
- После сбоя читатель никогда не получает смешанный пакет.
- Orphan `.staging-*` не считается активным поколением и не удаляется автоматически до появления безопасной descriptor-relative очистки.
- Публикация не должна проходить через изменяемый промежуточный `.staging/` каталог.
- Существующее generation directory никогда не удаляется или заменяется в ходе commit без отдельного доказательства его безопасного состояния.
- В первой версии нет конкурентного GC опубликованных поколений.
- Тесты покрывают каждый crash point и stale writer.
- Гарантии ограничены проверенной ОС и локальной файловой системой.
